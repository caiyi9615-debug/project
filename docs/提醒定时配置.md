# 免费到期提醒：外部定时调用与状态核对

本指南复用现有 Render Free、Supabase 提醒队列和浏览器订阅，不新增数据库或服务端定时器。浏览器通过 `/api/push/sync` 同步任务；只有外部服务调用 `/api/push/tick` 才会执行发送。`/api/health` 仅检查服务并触发唤醒，不会发送提醒。

Render 免费服务连续 15 分钟没有入站流量会休眠，再收到请求时唤醒约需一分钟。因此建议每 10 分钟先访问 health，再错开两分钟调用 tick，减少冷启动对发送的影响。免费服务的冷启动、网络和设备通知仍会延迟，不能保证严格准点。[Render 官方说明](https://render.com/docs/free)

## 1. 更新代码与现有 SQL

1. 按 [免费系统推送部署](免费系统推送部署.md) 完成既有 Supabase 项目、VAPID、Render 环境变量和设备订阅配置。邀请码 `PUSH_JOIN_CODE` 用于设备订阅，不是定时调用凭证。
2. 部署本次代码后，在同一个 Supabase 项目的 SQL Editor 重新执行仓库最新版 `deploy/push-schema.sql`。它更新既有函数，不要求新建数据库或删除提醒表。不要先删除表，以免丢失已有任务和发送记录。
3. 这次 SQL 更新取消领取提醒时“仅补发最近 15 分钟”的限制。只更新 Node.js 代码、没有更新云端函数，会使较早的漏发提醒仍无法被领取。
4. 初次开启提醒之前已经错过的阶段仍不追溯创建。补发针对已经同步进现有队列、尚未发送且任务截止时间未到的提醒。

`PUSH_CRON_SECRET` 的真实值只保存在 Render 的 Environment 和定时服务私有配置中。不要写入代码、本文、URL 查询参数、仓库、截图或 `.env` 提交。若已经泄露，在 Render 和定时服务两处同步轮换。

## 2. 用 cron-job.org 建立两个免费任务

[cron-job.org](https://cron-job.org/en/) 支持免费定时执行、自定义请求方法、请求头和请求体。注册后在控制台创建以下两个任务；不需要启用付费方案。

使用自己的 Render **HTTPS 服务地址**替换表中的“你的服务名”。两个任务都选择每天、每小时执行，时区统一选 `Asia/Shanghai`，分钟按下表设置；不要把每十分钟误设为每天某一个时刻。

| 设置 | 任务 A：唤醒 | 任务 B：发送提醒 |
| --- | --- | --- |
| URL | `https://你的服务名.onrender.com/api/health` | `https://你的服务名.onrender.com/api/push/tick` |
| 请求方法 | GET | POST |
| 分钟 | `0,10,20,30,40,50` | `2,12,22,32,42,52` |
| 请求体 | 留空 | `{}` |
| `Content-Type` 请求头 | 不需要 | `application/json` |
| `Authorization` 请求头 | 不需要 | 在私有输入框填 `Bearer ` 前缀，再接 Render 中 `PUSH_CRON_SECRET` 的同一真实值 |

在任务 B 的高级设置中添加自定义请求头。这里的 Bearer 凭证用于本项目接口，不是 cron-job.org 自身的管理 API key，也不是 DeepSeek 密钥。不要改成 Basic Authentication。[请求头与 POST 支持说明](https://cron-job.org/en/faq/)

分别启用任务失败、恢复成功和任务自动停用的邮件通知。保存后检查“下次执行时间”，确认任务 A 与 B 每次相差两分钟；不要让它们同时执行。[通知功能说明](https://cron-job.org/en/)

cron-job.org 的免费请求有 30 秒执行限制，不要把旧 Supabase Cron 配置中的 120 秒当作它的免费超时额度。首次 health 可能在 Render 唤醒完成前超时：先等待唤醒，再用“测试执行”重试；持续超时要检查服务状态，不能仅靠两分钟错峰断定已经恢复。[免费请求时限](https://cron-job.org/en/faq/)

如果原来启用了 `deploy/push-cron.sql` 建立的 `deadline-hunter-push`，待新任务测试通过后，在 Supabase Cron 界面暂停原任务，只保留一套发送定时器，避免增加无用请求。暂停定时器不会删除提醒队列。

## 3. 看返回结果与只读状态

先“测试执行”任务 A，确认 HTTP 200 且响应含 `ok:true`；再测试任务 B。tick 执行成功返回 HTTP 200，响应里的 `sent` 表示本次被推送服务接受的提醒条数；`sent:0` 也可能是正常结果，因为此刻没有应发送的任务。

查看状态时，在维护者使用的 HTTP 客户端中创建 GET 请求，地址为同一网站的 `/api/push/status`，添加与 tick 相同的 `Authorization` 请求头。也可以在定时服务中临时建立一个**不启用周期执行**的 GET 状态任务，仅手动测试；不要分享含请求头的配置截图。

status 是只读接口，不领取提醒、不发通知、不写数据库。授权通过时 HTTP 200 只表示状态查询成功；判断上次 tick 是否成功要看 `lastTick.ok`。

| 字段 | 维护者应检查的内容 |
| --- | --- |
| `configured` / `startedAt` | 既有推送环境变量是否齐全、当前进程的启动时间；configured 为 true 不代表云数据库可用 |
| `running` | 是否有 tick 正在执行；不要把“已有执行正在运行”当作本次完成 |
| `lastTick.startedAt` / `finishedAt` | 最近一次执行的开始、结束时间（UTC ISO 时间，末尾 `Z`）；北京时间加 8 小时 |
| `lastTick.ok` | 最近一次 tick 是否成功；失败时为 false，执行中为 null |
| `lastTick.claimed` / `sent` / `failed` / `skipped` | 本轮领取、发出、失败和跳过的数量；failed 还可能包含领取或补确认失败，不应当作独立任务总数 |
| `lastTick.error` | 固定错误说明；不会展示云数据库返回体、订阅地址或密钥 |
| `lastSuccessAt` | 最近一次完整成功的 tick 时间；失败后仍保留此前成功时间 |
| `pendingAcknowledgements` | 已被推送服务接受或已确认订阅失效，但结果尚未写回数据库的数量 |

上次执行记录和待确认列表保存在当前 Node.js 进程内存中，Render 休眠、重启或重新部署后会清空。尚未执行时 `lastTick` 为 null；没有执行记录不等于历史上从未发送，重启后的第一轮要结合定时服务执行历史核对。长期发送去重记录仍沿用现有 Supabase 队列的 `sent_at`，没有新增数据库。

## 4. 失败后的补发与去重

- 领取队列、读取订阅、推送请求或发送结果确认失败时，tick 返回 HTTP 503 和 `ok:false`，同时更新失败状态。定时服务应将它视为失败，而不是只检查 URL 能否访问。
- 下一轮 tick 会重新处理已到计划时间、尚未发送且 `due_at` 未到的队列记录。不会因为超过原先 15 分钟窗口就永久漏掉，也不会发送已经超过任务截止时间的提醒。任务已取消、已完成或截止时间已修改的同步规则保持不变。
- 每次最多领取 20 条；积压较多时要分后续 tick 处理，不能认为一次调用会清空全部积压。任务的不同提醒阶段有不同 ID，阶段之间不是重复消息。
- 已成功记入 `sent_at` 的同一条提醒不会重新领取；浏览器重复同步也不会清空其发送记录。
- 推送已成功但写回数据库失败时，当前进程先保留“待确认”记录。下一次 tick 优先补写确认，再领取新任务；确认仍失败时停止领取，以免在数据库不可用时重复发送。
- Web Push 与数据库不是同一事务。如果推送已被接受、数据库尚未确认期间进程崩溃或重启，内存保护会丢失，重试存在重复的可能；这不提供跨崩溃的严格“恰好一次”保证。推送服务接受消息也不代表设备已展示，离线、省电、勿扰和通知权限仍可能影响接收。

## 5. 做一次真实核对

1. 在目标设备开启通知，输入邀请码，发送测试通知，确认设备通知栏实际收到。这个测试只验证推送链路，不证明定时器运行。
2. 新建一个非演示、未提交、截止在当前北京时间后 35 分钟的任务，填明确日期与时间，并核实时间依据；同步提醒任务后关闭网页。
3. 核对定时服务的执行历史：health 返回成功后，tick 应按计划运行。查看 status 的最近时间和 `sent`，再确认设备实际收到通知。
4. 若要检查错误响应，在定时服务的临时测试副本中使用错误凭证，预期 HTTP 401；不要改坏正式任务或 Render 的真实配置。失败请求不能发送提醒。
5. 用量、免费额度和暂停情况在各服务后台检查。Render 的免费实例小时是整个工作区共享，持续唤醒会消耗额度；免费服务仍可能被平台重启或暂停。[免费额度与实例限制](https://render.com/docs/free)

| 现象 | 检查方法 |
| --- | --- |
| 401 | 检查 Bearer 前缀、空格及两端配置值是否一致，不要把邀请码当作定时凭证 |
| 405 / 415 | tick 必须 POST，并带 `Content-Type: application/json`；status 必须 GET |
| 409 / `busy:true` | 上一轮 tick 还在运行；本次未启动第二轮，不要把它当作成功发送 |
| 503 / `lastTick.ok:false` | 查 `lastTick.error`、Render 日志、Supabase 服务与 SQL 是否更新；下一轮会重试有效待发记录 |
| 定时服务超时 | 先访问 health，待唤醒后查询 status；超时可能发生在后端仍执行时，不能仅凭超时判定未发送 |
| health 正常但 tick 时间不更新 | 检查任务 B 是否启用、执行时间、凭证和失败记录；health 本身不触发 tick |
| `sent:0` | 检查任务是否同步、非演示、已确认且未提交、提醒时点是否已到；也可能已发送过或截止已过 |
| `sent` 增加但设备没收到 | 查浏览器/系统通知权限、设备网络与省电模式，并单独发测试通知 |

本次只提供配置说明和接口改进，没有替维护者创建外部任务、修改 Render 环境变量或验证真实线上通知。外部定时与推送均为免费服务，存在运行延迟和额度限制。
